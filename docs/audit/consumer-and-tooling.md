Audit date: 2026-10-23. Scope: the local `Projects/` checkouts listed below, with a deeper review of `FieldCore-node`, current external-owner drivers, example CLI contracts, native tests, CI, packaging and host HIL runners. This is a source audit; no sibling builds, tests, serial sessions, hardware operations or remote CI runs were performed. No sibling files were changed.

The user's `fieldcore-noce` most likely means the existing `FieldCore-node` repository. That is the consumer inspected here; the new library must not depend on it.

## Conventions that agree

- Public APIs use per-library namespaces and headers under `include/<Library>/`; `Status` is typically `Err code`, `int32_t detail`, and a static-lifetime `const char* msg`. Fallible calls report typed failures; no framework error types escape through public headers. Evidence: `PCA9555/include/PCA9555/Status.h:70`, `LDC1614/include/LDC1614/Status.h:35`, `LSM6DS3TR/include/LSM6DS3TR/Status.h:46`.
- Types use PascalCase; ordinary methods, locals and config fields use camelCase; private members commonly use `_camelCase`; library enum values/constants commonly use uppercase names. `LDC1614/AGENTS.md:225` and `LSM6DS3TR/AGENTS.md:262` agree. FieldCore uses its own `kPascalCase` constants and PascalCase enums (`FieldCore-node/AGENTS.md:121`); that is a consumer convention, not the chip-library default.
- Core and public headers are framework-neutral, allocation-bounded and logging-free. Board pins, transport handles, CLI colors, USB serial, timers, mutexes and GPIO setup live in examples/adapters. `MCP45HVX1/AGENTS.md:48`, `LDC1614/AGENTS.md:97` and `SHT3x-main/AGENTS.md:121` describe this explicitly.
- Arduino and native ESP-IDF examples are separate platform applications. Native IDF uses `app_main`, `driver/i2c_master.h`, native timing/task/console APIs and fixed buffers; it must not import Arduino facades. CLI parity is enforced by local contracts, not by making IDF compile Arduino sources (`MCP45HVX1/AGENTS.md:55`, `LSM6DS3TR/AGENTS.md:93`).
- `library.json` is the version source; generated `Version.h` is not hand-edited. The newer generators check the IDF manifest and Doxygen version too (`LDC1614/AGENTS.md:202`).
- Windows workflows use `scripts/pio.cmd` to locate the existing installation; no second PlatformIO Core is silently installed (`MB85RC/AGENTS.md:36`). Shared `Projects/AGENTS.md:3` requires focused local checks and exact-commit remote CI for substantial changes rather than repeated remote runs for small documentation edits.

## Differences the implementation agent must resolve explicitly

1. **Lifecycle names and side effects are not uniform.** PCA9555 `bind` and its `begin` alias are passive (`include/PCA9555/PCA9555.h:233`). TCA9548A `begin` includes presence detection (`AGENTS.md:168`). RV3032 passive `begin` coexists with an explicit special startup operation (`AGENTS.md:109`). SSD1315 passive `attach` coexists with legacy `begin/recover` sequences (`AGENTS.md:134`). Use the newest passive pattern for TUSB32x; there is no installed compatibility API requiring legacy synchronous startup.
2. **Health is not one shared contract.** TCA9548A object-lifetime success/failure counters saturate and its initial presence failure remains UNINIT (`AGENTS.md:203`, `:243`). RV3032 lifecycle counters wrap (`AGENTS.md:288`); MB85RC tracks wrapping totals plus a saturating streak (`README.md:353`). BME280 session totals saturate (`AGENTS.md:269`). SHT3x separates logical completions, physical callbacks, protocol faults and expected-not-ready outcomes (`AGENTS.md:256`, `:284`). LDC1614 and LSM6DS3TR remove driver offline/admission policy entirely (`LDC1614/AGENTS.md:195`, `LSM6DS3TR/AGENTS.md:219`). Recommendation: passive diagnostics with explicitly documented saturating counters; external/example health projection if desired. Never make an OFFLINE label suppress a requested diagnostic or dictate retries.
3. **Transport evidence varies.** PCA9555 uses `TransportResult` plus `WriteEffect` (`Config.h:23`); MB85RC returns a transport result (`Config.h:136`); LDC1614 and LSM6DS3TR use Status callbacks and conservatively track operation effects. TUSB mixed status/control and interrupt-ack writes need an explicit decision about not-attempted versus possibly-committed effects; do not infer "no effect" from timeout.
4. **The CLI code-sharing approach varies.** LDC1614 has independent fixed C++ tables checked against a host-only contract (`tools/ldc1614_cli_contract.py:2`); SHT3x shares a framework-neutral command processor checked against a host contract (`tools/sht3x_cli_contract.py:2`). Either is defensible. Framework-specific compatibility wrappers are not.
5. **IDF paths and versions vary.** `espidf_basic`, `idf/basic` and `esp_idf/basic` all exist. PCA9555 CI uses IDF v5.4 (`.github/workflows/ci.yml:143`); MB85RC tests v6.0.1 and v6.0.2 (`.github/workflows/ci.yml:102`); LDC1614 uses v6.0.2 (`.github/workflows/ci.yml:126`). Choose one consistent TUSB layout and an explicit version matrix after checking the current environment. Do not claim all siblings use a single path or toolchain.
6. **Package manifests are not proof of portability.** LDC1614, SCD41 and TCA9548A advertise wildcard frameworks/platforms; several others constrain discovery to Arduino/IDF on Espressif. Prove standalone compilation and an extracted-package consumer independently, then make metadata agree with that evidence.
7. **Release/workflow requirements differ.** TCA9548A documents exact reviewed commit/tag and downstream peeled-SHA pinning; RV3032 requires explicit tag authorization. A fresh promptset must inspect applicable TUSB instructions and current user authorization, not inherit sibling publication permission merely by copying a file.

## CLI and runner design lessons

The repeated common vocabulary is `help/?`, `version/ver`, `scan` or family-scoped discovery, `read`, `cfg/settings`, `drv/health`, `probe`, `verbose`, and bounded diagnostics. Cooperative newer drivers add `job/progress`, `result`, `cancel/stop`, explicit initialization and recovery/invalidation commands. Copy the common experience but only implement commands meaningful for USB Type-C configuration and status; EEPROM erase, sensor calibration, measurement compensation, framebuffer and coil commands are not reusable requirements.

`LDC1614/tools/ldc1614_cli_contract.py:24` defines execution classes (`CACHE_ONLY`, `PURE`, `ONE_TRANSFER`, `CORE_JOB`, `CLI_JOB`, `OWNER_BUS`, `LIFECYCLE`), safety classes and fixture classes. Command rows include canonical names, aliases, help syntax, output keys and prerequisites (`:58`, `:105`). This is a particularly useful starting point for a TUSB command contract, because it distinguishes reading a cached view from physical I/O and owner-only bus recovery. PCA9555's simpler checker verifies dispatch/help/confirmation strings (`tools/check_cli_contract.py:10`, `:66`, `:138`); do not rely only on source-token checks for behavioral correctness.

For TUSB32x, the promptset should require:

- Version/provenance and bus information without hardware mutation; cached health/progress/configuration separate from live register/status reads.
- Explicit confirmed controls for role/current advertisement, reset, interrupt acknowledgement, disable/enable policy and raw writes according to the vendor register semantics. A raw dump must not unknowingly acknowledge events, overwrite mixed-access bits, or initiate a mode change.
- Bounded parser input, exact arity/ranges, overflow and trailing-junk rejection, unknown-command behavior, finite output, color-disabled mode and ANSI-insensitive host parsing.
- A single command contract shared by help, implementations and parser expectations, including execution/side-effect/fixture classification and stable machine-readable status keys.
- An explicitly provided serial port; no port enumeration followed by unsolicited probing, flashing or reset. State baud, DTR/RTS behavior and boot settling. Support parser-only mode with no serial dependency and do not confuse it with hardware PASS.
- Transcript plus JSON and concise Markdown evidence; fixture identity, chip variant/address, build/runtime stack, host revision, firmware-reported revision, command timeouts, terminal outcome, effect/cleanup evidence and optional test skips. Host checkout SHA alone cannot prove flashed firmware.
- Nonzero failure verdict on malformed, missing, ambiguous, truncated, contradictory, restarted, timed-out or unmatched command output. Expected failures must be command-scoped. Never accept an echoed word `OK` as completion.
- Explicit opt-in fixture groups for mode changes, current advertisement, connect/disconnect orientations, IRQ wiring, resets, power disturbances and electrical fault cases. State-restoration must be verified or uncertainty retained; protocol success does not prove VBUS switching, connector wiring, power supply behavior or electrical USB compliance.

Concrete references: `LDC1614/tools/ldc1614_hil_runner.py:2` emits NOT_RUN without hardware, `:97` bounds/persists transcripts, `:2036` classifies command evidence, `:2206` checks contradictory identity and `:2276` matches target-reported firmware commit. `MB85RC/tools/hil_runner.py:202` validates health snapshots, `:347` classifies expected failures, `:1184` evaluates strict reasons; its DTR/RTS choices at `:771` illustrate behavior that must be made explicit rather than copied blindly.

## Verification and packaging requirements

Reference CI provides the shape, not prior proof for this library. PCA9555 separates Arduino builds, native tests, static/package/Doxygen checks and IDF builds; MB85RC adds metadata and strict HIL-parser tests; LDC1614 adds readiness-wording and clean-consumer checks. TCA9548A registers separate CLI, console, transport and no-Arduino suites (`platformio.ini:71`, `:93`, `:99`, `:105`, `:116`, `:127`), avoiding silent unregistered tests.

The TUSB promptset should require a documented focused command set plus a complete validation entrypoint, with:

1. Standalone C++17 core/public-header compilation without Arduino/IDF include paths; explicit clean extracted-package consumer build.
2. Native behavioral fake tests for exact bus bytes/masks, unsupported variant features, identity uncertainty, RMW and W1C handling, failure at every phase, ambiguous writes, callback budgets including zero, immutable deadline and wrap boundaries, cancellation, no-I2C snapshots, result retention/backpressure and caller recovery/invalidation.
3. A minimal external-owner fixture interleaving this chip with another fake device, showing fairness, one terminal callback per owner poll, time-only wait periods, timeout clipping, result delivery and no autonomous retries. The fixture uses no FieldCore headers.
4. Arduino ESP32-S2/S3 example builds, real native ESP-IDF example builds, example CLI behavioral tests, host parser/runner tests, contract guard tests and documented pinned build dependencies.
5. Generated-version drift, package contents, direct public includes, framework-boundary/timing guards, Doxygen and local documentation-link checks. Test source guards with negative fixtures so cosmetic code changes do not give false confidence.
6. HIL as a separately recorded physical qualification phase with exact firmware provenance and explicit NOT_RUN/SKIP results. Never declare electrical/connector functionality solely from a fake or native suite.

The deep LDC1614 native suite is useful evidence for *types of tests*: zero-I2C bind (`test/test_basic.cpp:520`), budgets (`:743`), failure/cancel/deadline matrices (`:3109`), result backpressure/exact take (`:3113`), owner interleaving (`:3115`), ambiguous effects (`:3117`), atomic publication (`:3121`) and passive diagnostics (`:3133`). Reuse the test principles, not chip-specific assumptions.

One audit caution: `MCP45HVX1/tools/validate.py:69` and `:77` print SKIP when tool prerequisites are absent, then return success at `:79`. A new complete-validation entrypoint should fail or explicitly classify incomplete validation so skipped mandatory compiler/PlatformIO checks cannot be mistaken for complete success.

## Promptset acceptance implications

Before **every** implementation phase, reread the applicable TUSB instructions, inspect sibling changes since this audit, and inspect the specific public code, examples, native registration and workflow commands relevant to that phase. Record changed assumptions and intentional divergences. Never use this date-stamped report as authority to ignore newer repository contracts.

The finished library should preserve the recognizable family naming, status vocabulary, package layout and diagnostic workflow while making its own ownership, variant, register, lifetime, health and effect contracts explicit. A standalone application, a bare-metal owner loop, a native IDF task and a FieldCore-style wrapper must all consume the same chip core without another framework or product dependency.
